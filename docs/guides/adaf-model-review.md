## Appendix

<details><summary><b>Detector caveats — how to read a 🔴 / 🟠</b></summary>

The detectors are deterministic but heuristic about *which column plays which role*:

- **MD-01** counts a model-level `unique` **or** `dbt_utils.unique_combination_of_columns` as a grain test. So an MD-01 false positive means *a uniqueness test exists* — if the LLM wanted an explicit `unique_combination_of_columns`, that is a stricter style, not a hallucinated fact.
- **EN-01** infers the PK as `<model>_id` or the **sole** `*_id`/`*_uuid` column; a model with several key columns yields *no identifiable PK* → n/a (a detector limit, hence 🟠 — not an LLM error).
- **EN-03** treats every non-PK `*_id`/`*_uuid` as a FK needing `relationships`; it may over-include a key when the PK isn't identified.
- **TM-SC-03** needs `catalog.json` (a build) to see column types; without it, n/a.
- Columns are warehouse-resolved from `catalog.json` when present, else YAML-declared.

</details>
